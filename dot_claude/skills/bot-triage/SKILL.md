# Bot Triage

Triages the dependency- and security-bot PRs and the Dependabot security alerts
across a set of repos, so you see at a glance what's a routine bump versus a
security issue, and which alerts have no fixing PR yet.

The mechanical fetch is one read-only helper bundled with this skill. Run it as
`bash ~/.claude/skills/bot-triage/bot-triage.sh <owner/repo>`. It returns JSON
per repo; this skill runs it per repo and turns the results into the report.
Don't re-implement its `gh` calls inline.

## Step 0 — tools on PATH

Non-interactive shells here often lack the mise tools. Try `gh` directly; fall
back to `mise exec -- gh`. The helper itself needs `gh` and `jq`.

## Repo set

The repos to triage are a personal choice. There's NO default list in the repo:
the list lives only in memory (see [[dependency-bot-repos]]), and only once you
have chosen to save one. It is not project config.

1. Resolve the list, in order: repos named in this invocation win for this run
   (add/remove/replace); else the saved memory list if one exists; else ask,
   because nothing is seeded by default. Never guess a repo name.
2. The helper validates each repo against GitHub (`gh repo view`) and exits
   non-zero on a bad one. On that error, re-ask for the correct repo instead of
   proceeding.
3. Persist only on request: if you ask to remember the list, write/update the
   `[[dependency-bot-repos]]` memory file. Don't create it unprompted.

## Procedure

For each repo, run the helper and read its JSON (`pull_requests[]` with
`number`, `title`, `url`, `section`, `is_security`, `checks.state`, `draft`;
`alerts` with `total`, `by_severity`, `items[]` each with `url`; `security_url`).
The repos are independent, so issue the per-repo helper runs concurrently and
collect the results; you still classify and correlate every result yourself
below.

- **Classify, don't just list.** Each bot PR already carries a `section`
  (dependabot / frogbot / sdk-gen / release / mise / renovate / other-bot) and
  an `is_security` flag.
- **Correlate alerts to PRs.** For each security alert, check whether an open PR
  resolves it (same package/manifest). What matters is the alerts with NO fixing
  PR; those are the ones to surface. The `gh` API alert count can differ from
  the Security tab UI count; the API is the source of truth.
- **Autogenerated repos: skip their alerts.** Some repos are autogenerated
  (contents can't be hand-edited; a fix goes through the generator, not the
  repo), so their security alerts aren't actionable gaps and must NOT be
  surfaced. Which repos those are is a marking you provide, saved alongside the
  repo list (see [[dependency-bot-repos]]), never inferred from the name
  (`dailypay-sdk-sample-apps` has "sdk" in its name but is real code). Still list
  these repos' open bot PRs normally; only their alerts are suppressed. Persist a
  change to this marking only on request, same as the repo list.
- **Checks matter for safety.** A green bump is low-risk; a failing one isn't.
  Use `checks.state` to judge, mention it only when it's failing.

## Output

Chat response, voiced via `writing` for any prose. Group by repo. For each repo,
list every open bot PR as a link, then, only if there are security alerts with
no fixing PR, list those below the PRs and link to the page where they're viewed
(`security_url`). Shape per repo:

```text
**<repo>**
PRs:

- <PR title>: <url>
- <PR title>: <url>

Security (no fixing PR): <package/advisory>, <package/advisory>
<security_url>
```

Omit the `Security` block entirely when every alert is covered by a PR (or there
are none), and for autogenerated repos always omit it. If a repo has no open bot
PRs but does have uncovered alerts, keep the `PRs:` line with "none" so the gap
is obvious. Lead the whole message with the repos that have uncovered security
alerts. Keep it scannable: no per-PR prose, just the links; add a one-line note
after a PR only when its checks are failing.

## Scope and safety

Read-only, always. Never merge (merging is a human action, no exceptions) and
never comment. The most you can opt into per run is auto-approving a PR, and only
when its checks are green and repo permissions allow it (`gh pr review` is
human-gated today, so it prompts). Default behavior is report-only.

## Before delivering

Confirm every repo in the resolved list was triaged (or its access error
reported), and that alert-to-PR correlation was actually checked, not assumed.
Counts you report come from the helper output, not memory.
